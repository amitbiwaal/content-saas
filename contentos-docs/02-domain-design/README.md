# 02 — Domain Design

The business domain model of ContentOS AI. This folder sits between the approved architecture (`01-system-architecture/`) and the physical schema (`03-database/`): **tables are derived from these models, never invented directly.** Where a table exists that no aggregate here justifies, it is a defect.

Every document specifies aggregates, aggregate roots, entities, value objects, domain services, invariants, lifecycle state machines, and domain events for one area. Behaviour lives in aggregates; infrastructure lives elsewhere.

**No new bounded contexts are introduced here.** These seven documents cover nine of the eleven approved contexts. The remaining two — **Commerce** (Plan, Subscription, CreditLedger) and **Notification** (Channel, Preference, Delivery) — are documented with their platform services in `04-platform/billing.md`, `04-platform/credits.md`, and `04-platform/notifications.md`, because their models are inseparable from those services. `organizations.md` specifies the Identity ↔ Commerce boundary; it does not model Commerce itself.

## Rules binding every document in this folder

**Tenancy is final** (ADR-017). Every aggregate sits at a fixed position in this hierarchy:

```
User → Organization → Workspace → Project → Article → (Revisions · Reports · Publish attempts · Snapshots)
```

- `tenant_id` **is the workspace identifier** and is the row-level isolation key on every table.
- `organization_id` is the **commercial and administrative boundary** — billing, SSO, org roles, audit aggregation — and is carried on workspace-owned aggregates so org-scoped queries never join across tenants.
- An aggregate that cannot state its `tenant_id` does not belong in this folder. The two exceptions are `User` and `Organization` themselves, which sit above the workspace boundary and are explicitly documented as such in `organizations.md`.

**Aggregate boundaries stay small.** An aggregate is a consistency boundary, not a convenience container. Prefer referencing another aggregate by identifier over nesting it. Where a large object graph looks natural — an Article with all its revisions, reports, and attempts — it is deliberately split into separate aggregate roots that reference `article_id`, because they have different write frequencies, lifetimes, and immutability rules.

**Events follow ADR-020, without exception.** A domain event is written to the transactional outbox **inside the same transaction** as the state change that produced it. The Outbox Relay publishes to Redis Streams; consumers read through consumer groups and deduplicate by `eventId`. No aggregate, service, or handler publishes directly to a bus, and no event is emitted for a transaction that has not committed. Envelope, delivery semantics, retry, and DLQ behaviour: `01-system-architecture/10-event-flow.md`.

**Scoring is not defined here.** Review, SEO, Optimization, and Refresh all produce measures, and the ownership question — who computes what, on what scale, who aggregates — is the proposed **ADR-021 / OQ-23**, still open. These documents therefore define *where a score attaches* and *what an aggregate does with a verdict*, and never a scoring algorithm or weighting. A document that invents one contradicts a pending decision.

**Vocabulary is fixed** by `01-system-architecture/05-glossary.md`. Terms are used exactly as defined there — `Article` is the long-lived aggregate, `ArticleVersion` is `(article_id, revision_number)`, a verdict is exactly `pass` / `soft-warn` / `block`, `tenant` always means workspace, and "agent" is banned.

## Conventions applied uniformly

| Concern | Convention |
|---|---|
| Identifiers | UUID v7 — time-ordered, index-friendly, generated by the application |
| Audit fields | Every table: `created_at`, `updated_at`, `created_by`, `updated_by` |
| Soft delete | `deleted_at TIMESTAMPTZ NULL` on user-deletable aggregates; repositories filter it; a purge job hard-deletes after 30 days |
| Append-only | Revisions, publish attempts, performance snapshots, ledger entries, and audit rows are **never** updated or soft-deleted; corrections are new rows |
| Optimistic concurrency | A `version` integer on every mutable aggregate root; a stale write fails rather than silently overwriting |
| Timestamps | `TIMESTAMPTZ`, UTC, sourced from an injected clock so behaviour is testable |
| Explainability | Any aggregate producing a recommendation carries an Explainability Envelope: `{ recommendation, reason, evidence[], expected_impact, confidence }` (ADR-009) |

## How to read a document here

Each follows one order: Overview → Responsibilities → Domain Model → Business Rules → Lifecycle → Domain Events → Relationships → Database Impact → API Impact → Security → Performance → Failure Handling → Observability → Future Expansion → Cross References.

The two sections that matter most for implementation are **Business Rules** and **Lifecycle**. Between them they specify every invariant a code generator must enforce and every state transition it must permit or refuse. If an implementation question is not answered by those two sections, that is a documentation defect to be raised — not a gap to be filled by assumption (`01-system-architecture/12-architecture-decisions.md`).
